# VARVAR — правила проєкту (для кожного агента команди)

Система для закладу **Varvar Food Bar** (Буковель): каса (POS), 3 Telegram-боти, меню гостя з замовленням, сайт-візитка, доставка, кур'єри, склад, зарплата, броні. Інтерфейс і коментарі — **українською**.

## Стек
- **Сервер:** Cloudflare Worker `varvar-menu` (`worker/`, `wrangler.toml`).
  - Уся база — один Durable Object `Store` (`worker/src/store.js`). Запити до бази виконуються *всередині* нього (`handle()` з `index.js`) — один платний запит на дію.
  - `env.DB` має API як KV: `get/put/delete/getMany/list`.
  - **Під замком** (`L(env, keys, fn)` з `ops.js`) — будь-яке «прочитав → змінив → записав».
- **Каса:** `pos.html` + `js/pos/NN-розділ.js` → збірка `js/pos.build.js`.
  - Усі файли розділів склеюються в **одну функцію** (спільні `S`, `api`, `act`, `modal`, `ask`, `choose`, `toast`, `esc`, `money`, `tn`…).
  - **Не** ES-модулі.
- **Сайт гостя:** `index.html` + `js/app.js` (меню залу за QR; режим `?go` — з собою / доставка; `?go&book=ID` — передзамовлення до броні).
- **Візитка:** `about.html` + `js/about.js` + `css/about.css`.
- **Кухня на старому iPad:** `worker/src/kitchen.js` (ES5, `/k`).
- **Хостинг сайту:** файли сайту роздає сам сервер (Cloudflare static assets, `tools/build-site.sh` → `worker/.site`). Сайт викладається разом із сервером: `sh tools/deploy.sh`. GitHub — лише сховище коду (приватне).

## Збірка й перевірка
- **Каса:** `sh tools/build-pos.sh` (тести збирають самі). `?v=` у сторінках **піднімати не треба** — при викладанні `tools/stamp.mjs` ставить відбиток вмісту кожного файлу.
- **Перевірка сервера:** `cd worker && npx wrangler deploy --dry-run`.
- **Тестовий сервер — тільки launch-конфіг `worker-test`** (копія в `../.varvar-test`, без справжнього Telegram). Перед запуском: `rsync -a worker/src/ ../.varvar-test/worker/src/`.
  - Конфіг `worker` **не запускати**: там справжні ключі → повідомлення в робочу групу персоналу.
- **Каса на тестовому:** `http://localhost:8000/pos.html?api=http://localhost:8787` (launch-конфіг `site`).
- **Автотести (обов'язково перед здачею роботи):** з кореня СВОЄЇ копії `sh tools/test.sh` (`--api-only` / `--ui-only`). Скрипт сам бере чергу (замок), заливає твій сервер і сайт у спільне тестове середовище (`worker-test` :8787 + `site-test` :8001 — мають бути запущені launch-конфігами) і проганяє `tools/selftest.mjs`. **Ніколи не роби rsync у `.varvar-test` вручну** — перезапишеш колегу. Опис — `_team/qa.md`. Усе має бути ✅.
- **Після зміни інтерфейсу** — перевірити у браузері: консоль без помилок, текст не вилазить за картки (телефон 375, вузьке вікно 880, широке 1280).

## 🛡 Як не ламати старе (фундамент)
- **Де що лежить** — `_team/map.md` (генерується сам): файл → що робить, op → де обробляється і хто викликає, функції розділів каси з рядками, ключ бази → які файли його чіпають. Спершу дивись туди, потім `grep`.
- **Перед зміною ключа бази** (`bill:`, `att:`…) — глянь у карті всі файли, що його чіпають, і перевір кожен.
- **`tools/check.mjs`** (сам на початку `test.sh`, ~3 с): дубль назви між розділами каси (тихо перетирали одна одну), синтаксис, `import { X }` неіснуючої назви на сервері, кнопки й op без обробника.
- **💨 Димовий тест** у `selftest.mjs`: кожна дія каси з порожніми даними не має давати 500. Нова op потрапляє туди сама.
- **🤖 Димовий тест бота**: адмін входить за PIN і натискає кожну кнопку клавіатури та inline-кнопку (без аргументів, крім небезпечних). **🖱 Тест кліків каси**: кожна кнопка `data-a` у кожній вкладці натискається без помилки в консолі.
- **🔎 `tools/undef.mjs`** (у check.mjs): назва з іншої частини `ops-*`/`bot-*` використана без `import`.
- **Нова op або зміна поведінки — свій тест** у `selftest.mjs` (успіх + головна заборона). Без тесту фіча вважається незданою.
- **`ops.js` і `bot.js` — вітрини**: інші файли імпортують з них, як і раніше; сам код — у `ops-*.js` / `bot-*.js`. Нову функцію клади у файл своєї теми й додай у вітрину. Великий файл ділиться `tools/split.mjs` (переносить код без змін і сам ставить імпорти).
- Не переписувати чужий код «заодно»: одна правка — одна мета; перенесення коду між файлами — окремим комітом без зміни логіки.

## Правила
- **Паритет каса ⇄ бот персоналу:** нова дія в касі має бути і в боті (і навпаки).
- **Ніколи** не публікувати `printer/varvar-print.config.json`.
- **Секрети** — лише `wrangler secret put` (`BOT_TOKEN`, `GUEST_BOT_TOKEN`, `COURIER_BOT_TOKEN`, `TG_SECRET`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `KIMI_API_KEY` (запасні ШІ), `BREVO_KEY`, `MAIL_FROM` (листи)…). У код і чат — ні.
- **Деплой, push і злиття в `main` робить лише керівник.** Працівник **комітить у своїй гілці** (worktree), тестує через `sh tools/test.sh`, надсилає звіт.
- Тимчасових тестових працівників / замовлень на робочому сервері не створювати; на тестовому — можна.
- Тестові кнопки («Обнулити все», «Видалити закритий») не прибирати, доки не скаже власник.
- **Стиль каси:** темна тема, змінні `--card/--card2/--accent…`, картки `.card` з `h3`, рядки `.kv`, кнопки `.btn sm`, перемикачі `.switch`.
  - Довгий текст — переноситься, не вилазить.
  - Коротко, з емодзі на початку підпису.
- **Коміти** закінчуються рядком `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## 💸 Регламент команди — економно, без втрати якості
Ліміт підписки спільний, тож кожен зайвий прогін чи прочитаний файл коштує.
- **Читай мінімум:** цей файл + паспорт свого розділу (`_team/<розділ>.md`). Код — через `grep -n` і `sed -n 'рядки'` у потрібних місцях, а не файл цілком. Паспорти інших розділів — лише якщо твоя зміна їх зачіпає.
- **Тести під час роботи — вибірково і тихо:**
  - сервер: `sh tools/test.sh --api-only --quiet`;
  - інтерфейс лише свого розділу: `sh tools/test.sh --ui-only --quiet --views=<свої view> [--roles=…] [--widths=375,1280]`.
  - **Повний прогін (усі ролі й ширини) робить керівник** один раз перед викладанням. Агенту — лише якщо змінював спільне ядро (`00-core.js`, `ops.js`, `store.js`, `index.js`).
- **Без зайвих скриншотів:** перевіряй текстом (`read_page`, `javascript_tool`); скриншот — лише щоб показати результат або коли вигляд неможливо перевірити інакше.
- **Один прогін — одна правка.** Не запускай тести «про всяк випадок» без змін у коді.
- **Звіт керівнику — до 10 рядків:** гілка й коміт; що зроблено (по пунктах завдання); результат тестів одним рядком; ризики. Без переказу коду.
- **Перед звітом:** `git merge main` у свою гілку, коміт, тести. Керівник зливає без переробок.
- Нове завдання від керівника в тому ж вікні — продовжуй у тому самому контексті, не перечитуй усе спочатку.

## 🏪 Мультизаклад (платформа)
Система продається іншим закладам: кожен заклад — свій Durable Object, адреса `/v/<id>/…`, VARVAR = `varvar` (DO «main»). **Ніколи** не зберігати стан закладу в глобальних змінних модулів (лише `env` / контекст `cur()` з `venue.js`); посилання на сайт — `siteLink()`; секрети закладу — `cfg:secrets`. Подробиці — `_team/platform.md`.
- **Фундамент на тисячі закладів:**
  - ⏰ **Фонові справи** — у будильнику самого закладу (`store.js` `alarm()`), а не в центральному cron. Новий фоновий обов'язок додається в `cron()` (`site.js`) і повідомляє, коли прокинутись, через `soon(t)`.
  - 🧬 **Зміна формату даних** — лише нова міграція в `worker/src/migrate.js`. Стару міграцію не змінювати й не видаляти. Код має читати і старий формат: відкат версії не відкочує дані.
  - 🌐 **Реєстр (HUB)** — без обходу всіх закладів на кожен запит. Перебір робиться всередині `Hub` (`billScan`, `venueCount`).
  - 🚀 **Викладання сервера** — `sh tools/deploy.sh`: тести → деплой → перевірка → авто-відкат. Ручний відкат: `sh tools/deploy.sh --rollback`. **Дорожня карта — `_team/roadmap.md`** (на «що по плану?» — наступний пункт звідти).

## 🔍 Аудит командою (рідко)
Основне використання команди — **аудит системи на помилки** (розрахунки, логіка, зв'язки, кнопки, завершеність ланцюжків), а не написання коду. Правила, склад і формат звіту — `_team/audit.md`. Перед аудитом керівник проганяє `node tools/audit-static.mjs` і `sh tools/test.sh`. Аудитори не виправляють — лише знаходять з доказом; спілкуються між собою через `SendMessage`.
