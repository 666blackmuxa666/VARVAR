Архів по місяцях.** `arch:<YYYY-MM>` = gzip JSON місяця (closed+day+z+att), шматки ≤100 КБ (ліміт значення в DO), переносить нічний cron для місяців старших 18 міс.; читачі (`getClosed`, `reportRange`, `dayRecord`, звіти) читають спершу живий ключ, потім архів → формат старих даних не ламається; міграції не треба (лінивий перенос), у `migrate.js` лише маркер версії архіву.
**B. Бекап.** Тиждень: повний, розбитий на частини ≤20 МБ (ліміт KV-значення 25 МБ → ключі `bak:<заклад>:<тиждень>:<n>`); ніч: лише змінені ключі (Store вже має `changed()` → накопичувати «брудні» ключі, дельта = їхні значення + список видалених). Зберігання в KV: 8 дельт + 5 тижневих. Відновлення = тиждень + дельти по порядку (у консолі платформи).
**C. Копія поза Cloudflare.** Раз на тиждень повний набір частин (без токенів сесій — спільний фільтр з п.2) → AES-GCM (ключ `BACKUP_KEY` лише wrangler secret; на заклад — HKDF(BACKUP_KEY, venue)) → S3-сумісне сховище (Backblaze B2 / AWS S3) підписаним запитом SigV4 з Worker (fetch, без SDK). Секрети: `S3_ENDPOINT`, `S3_BUCKET`, `S3_KEY_ID`, `S3_SECRET`, `BACKUP_KEY` — лише `wrangler secret put` (власник ставить сам). Локальний скрипт `tools/restore-offsite.mjs` розшифровує й збирає dump. Зберігання у бакеті: 8 тижневих + помісячні назавжди.
**D. Сповіщення** адміну платформи (група VARVAR платформи): база >70% ліміту (SQLite DO — `storage.sql.databaseSize`; якщо KV-бекенд — оцінка за довжиною dump, раз на тиждень) і будь-який збій бекапу/вивантаження (наразі збій лише `console.log`).
**E. Кнопка власнику «Завантажити весь заклад»** — `/__int/bak do:'export'` частинами, без токенів сесій і лічильників, запис у журнал.
Залежності: п.2 (фільтр токенів у dump) — спільна основа для B, C, E; блок на п.1/2 — дозвіл на зміни входу (див. вище), але A–E входу не чіпають. Рішення власника: провайдер (B2 чи S3) і що вважати «заклад завеликий».
