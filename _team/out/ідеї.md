## Раунд 2 (СТАРТ від 👑): дослідження інтеграцій + ТЗ

### A. iiko / Syrve API — висновок
- Є два публічні API: **iiko Cloud** (`api-ru.iiko.services`) і **Syrve API** (`api-eu.syrve.live`). Типове використання: тягнути меню/категорії/модифікатори/стоп-лист, штовхати замовлення, отримувати статуси; вебхуки для стоп-листа й статусів існують (за сторонніми плагінами; повний перелік подій не перевірено).
- Ціни за API **не публікуються**. Syrve продає ПЗ підпискою (~£49/міс на касу, Basic), для інтеграторів є партнерська програма (Tech Partner з щорічною сертифікацією).
- **Висновок: для Varvar і платформи ATOM — не пріоритет.** ATOM сам є касою, iiko — конкурент, а не джерело. Має сенс лише ЯКЩО заклад-клієнт уже сидить на iiko й хоче залишити її касою: тоді ATOM береться за гостьову частину (меню/QR/броні/доставка), а замовлення штовхає в iiko. Складність висока (мапінг меню, організації, термінали, сертифікація), ціна — переговори. Рішення: **відкласти до першого реального клієнта з iiko**; тоді спершу запитати доступ до docs і умови.

### B. Wolt / Glovo / Bolt Food — висновок
- Прямого відкритого API для українських закладів не знайдено; доступ — через партнерську угоду кожної платформи. Архітектура (за прикладом Wolt Order API v2): платформа шле нове замовлення в касу → каса підтверджує/відхиляє → каса повертає статуси (готово/скасовано) → окремо синхрон меню/стоп-листа.
- Є посередник **GetOrder** (UA): Glovo, Bolt Food, Wolt, Uber Eats ↔ Poster/Profit/Smart Touch, заявлено 1400+ закладів. Тобто конкуренти (Poster) підключають агрегатори саме так. Дані з пресу — не перевірені.
- **Висновок:** реально — не писати 3 прямі інтеграції, а або (1) інтегруватись із GetOrder-подібним хабом одним адаптером, або (2) отримати партнерство Wolt/Glovo і зробити один вхідний ендпоінт `/api/agg` у загальному форматі. Складність: висока (угоди, сертифікація, 3 різні формати). Цінність: висока для міст, **низька для Буковеля** (мало агрегаторної доставки). Рішення: **відкласти**; перший крок — запит до GetOrder про умови й API для ATOM (це дія людини, не код). Внутрішня підготовка (дешево): у замовленні доставки вже є `src`; додати джерело `agg:<платформа>` — пізніше.

### C. ТЗ-1: Waitlist у залі + «стіл вільний» (Р-2)
**Мета:** гість без броні, коли зал повний, стає в чергу; коли стіл звільняється — отримує повідомлення в Telegram/на сторінці.
**Дані (мінімум запитів):** один ключ `wl:<день>` → масив `{id, name, phone|tg, people, at, st: wait|called|seated|gone, tid?, cAt?}`; TTL 24 год. Жодних нових ключів на гостя. Запис — під замком `L(env,['wl'],…)`; зчитування залом — разом зі станом столів (вже робиться одним запитом), без окремого полінгу.
**Гість:** на `about.html`/`app.js` кнопка «Зал повний — стати в чергу» (ім'я, тел., кількість людей) → `POST /api/wl` (ліміт IP як у `/api/book`) → повертає `{id, pos, etaMin}`; сторінка статусу `GET /api/wl?id` з одним запитом кожні 30–60 с (не 3 с) і лише поки вкладка видима. Скасування `POST /api/wl {id, cancel}`.
**Каса:** розділ «Зал» — смужка «⏳ Черга (N)»: картки з іменем/людьми/очікуванням; кнопки «🔔 Покликати» (ставить `called`, шле гостю), «🪑 Посадити» (вибрати стіл → `seated`), «✖ Пішов». Підказка: при закритті рахунку столу з місткістю ≥ людей першого в черзі — тост «Стіл N вільний — покликати Ім'я?» (без авто-відправки).
**Бот персоналу (паритет):** команда/кнопка «⏳ Черга» зі списком і тими ж 3 діями (`waiter.js`/`bot.js` викликають ту саму `wlAct(env,id,act,arg)` — єдина функція для каси й бота).
**Гість-повідомлення:** через `guestbot.js` (якщо гість зайшов через бота) або SMS/сторінка; без нових платних каналів. «Покликати» повторно — не частіше 1 разу на 2 хв.
**Фон:** авто-`gone` через 20 хв після `called` без реакції — у `cron()` з `soon(cAt+20*60e3)`; нічого в центральному cron.
**Поза обсягом:** передбачення часу очікування ШІ; платна бронь.
**Тести:** API — створення/позиція/скасування/виклик/посадка, ліміти; UI — view hall із чергою. **Ризики:** спам (ліміт IP + телефон), гонка «посадити двох на один стіл» (проверка під замком).

### D. ТЗ-2: Живе відстеження кур'єра для гостя (Р-2)
**Мета:** гість доставки бачить «кур'єр їде» і ETA; опційно — точку на карті.
**Рівні (робити по порядку):**
1. **Без GPS (дешево, робити першим):** сторінка гостя (`?go` статус) показує кроки `прийнято → готується → кур'єр взяв → в дорозі → доставлено` з ім'ям кур'єра та «буду о HH:MM» (вже є `courAct 'eta'` → `go.at`). Дані беремо з уже існуючого `go` (`st`, `cour`, `takeAt`, `at`). Один `GET /api/gost?id` з кешем MEM 15–20 с (як `/api/goinfo`) і поллінгом гостя раз на 20 с лише на видимій вкладці.
2. **GPS (після 1):** кур'єр у боті кур'єрів ділиться Telegram **Live Location** (нативно, без нашого застосунку). Вебхук `courUpdate` ловить `edited_message.location` → зберігаємо в **пам'яті DO/ключі `cl:<ім'я>` `{lat,lng,ts}` лише якщо є активна доставка `road`** і не частіше 1 разу на 20 с (відкидаємо решту до запису — ніяких записів на кожну оновлену точку). Гість отримує координату в `/api/gost` (тільки для доставки в статусі `road`, не раніше «в дорозі»; після `done` — ключ видаляється).
3. **Карта:** проста мініатюра (Leaflet/OSM-тайли або посилання «Відкрити на карті»), без платного Google Maps.
**Каса:** у картці доставки значок «📍 жива точка · N с тому» + кнопка «карта»; у боті персоналу — той самий рядок у картці доставки (паритет). Адмін може вимкнути трекінг глобально (`gocfg.track`).
**Приватність:** показуємо кур'єра гостю лише під час `road`; у журнал координати не пишемо; кур'єр сам вмикає Live Location (згода), у регламенті зазначити.
**Запити CF:** вебхук Telegram оновлення на 20 с = ~3/хв на активного кур'єра — тільки під час поїздки; гості читають з MEM-кешу, тож ~1 звернення до DO на 15–20 с незалежно від кількості гостей.
**Поза обсягом:** маршрути/ETA від карт-сервісу, push.
**Тести:** API — `gost` повертає кроки; координата не віддається до `road`/після `done`; throttle запису. **Ризики:** Telegram Live Location може обірватись (показуємо «давно не оновлювалось» після 2 хв).

## ТЗ-2 рівень 2: GPS кур'єра для гостя (коротко, без коду)
1. **Джерело:** кур'єр у боті кур'єрів ділиться Telegram **Live Location** (нативно, без застосунку). Telegram шле `edited_message.location` у вебхук `tg3` при кожній зміні (зазвичай кожні кілька секунд у русі) — частоту ми не контролюємо.
2. **Відсікання до бази:** у зовнішньому Worker (`index.js`, до виклику DO) для `tg3` з `edited_message.location` — відкидати (200 OK) оновлення частіше ніж раз на 60 с на кур'єра (MEM-карта `chat_id → ts`). Ізолят може скинутись — тоді просто пройде зайве оновлення, не помилка. Без цього кожне оновлення = запит у DO.
3. **Запис:** у DO `courUpdate` — лише якщо в кур'єра є активна доставка зі `st='road'`; координата пишеться в наявний `ord:<oid>` полем `loc:{la,lo,ts}` (той самий ключ, що вже читає `/api/orders`) — **нового ключа немає**, одна `put` на хвилину. Поза `road` і після `done` поле видаляється/не пишеться.
4. **Читання гостем:** `/api/orders?g=1` вже в MEM-кеші 15 с і ходить у DO ≤ 1 раз на 15 с на унікальний набір id; `loc` додається в ту саму відповідь (+~40 байт). Нових ендпоінтів і додаткових звернень до DO — 0. Гість у режимі `?go` без таймера: оновлення при відкритті, поверненні на вкладку і кнопкою «🔄» (вже є).
5. **Що бачить гість:** у статусі «в дорозі» блок «📍 кур'єр на карті» — вбудований OSM (`openstreetmap.org/export/embed.html?marker=la,lo`, без бібліотек і ключів) + посилання «Відкрити в картах». Позначка «оновлено N хв тому»; якщо `ts` старіший 3 хв — «зв'язок з кур'єром втрачено», карта ховається.
6. **Відстань:** потребує координат адреси. Варіант A (рекомендую): необов'язкова кнопка «📍 Вказати мою точку» у формі доставки (`navigator.geolocation`, зберігається в `go.dst`), тоді відстань рахується на клієнті (гаверсинус) — без геокодера й запитів. Без неї показуємо лише карту. Варіант B (геокодування адреси) — платний/зовнішній, не робити.
7. **Паритет каса ⇄ бот:** у картці доставки в касі й у боті персоналу рядок «📍 N хв тому» + посилання на точку (читається з того ж `ord:`/bill, без нового запиту); адмін-перемикач `gocfg.track` вмикає/вимикає функцію цілком (за замовч. вимк.).
8. **Оцінка запитів на одну доставку (поїздка 25 хв):** Worker-запитів від Telegram ≈ кількість оновлень (до сотень, дешеві, відсікаються в Worker), **запитів у DO ≈ 25** (1/хв) + читання гостем ≤ 100 (25 хв ÷ 15 с, лише якщо гість тисне/повертається; зазвичай 3–10). Разом ≈ 30–125 DO-запитів на доставку; при 20 доставках/день ≈ 600–2500. Поточне опитування таблиць каси цього не збільшує.
9. **Приватність і ризики:** координата живе лише під час `road` і до 12 год у `ord:` (TTL існуючий), у журнали/звіти не потрапляє; кур'єр сам вмикає Live Location (внести в регламент). Ризики: кур'єр забув ділитись (тоді «зв'язок втрачено» — не шкодить), Live Location обривається через 8 год/вимкнення, точність у горах Буковеля.
10. **Обсяг:** `courier.js` (ловимо location + throttle), `index.js` (відсікання до DO), `index.js /api/orders` (+loc), `app.js` (блок карти), `delivery.js`/каса/бот (рядок і перемикач), міграція не потрібна (нове необовʼязкове поле). Складність середня; 1 сесія розробника + тест на подвійний `road`/`done`.
