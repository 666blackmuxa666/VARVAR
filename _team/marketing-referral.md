# 📣 Реферальна програма ATOM — ТЗ для розробки (чернетка, не вбудовано)

Рішення власника (2026-10-16): реферальна програма — так; нарахування спершу вручну. Цей документ — що саме будувати й які ліміти. Пункти 🔎 — рішення власника перед запуском. Нічого не опубліковано.

## 1. Правила для людей (те, що побачить користувач)
1. Ви привели заклад → коли він **вперше заплатив** (не пробний місяць, не заявка), вам **+1 місяць ATOM у подарунок**, приведеному — теж **+1 місяць**.
2. Подарунок = продовження `paidTill` на 30 днів (без грошей, без виводу).
3. Максимум **12 подарункових місяців на одного рефері** (🔎 [N]); далі — діє, але нових місяців не додає.
4. Посилання: `posatom.online/?ref=КОД`; код — у кабінеті закладу («🎁 Запросити друга»).
5. Не-клієнти (бухгалтер, консультант, друг): замість місяця — **🔎 [N]% з першої оплати привеблених або знижка**; виплати — вручну власником, не автоматично.
6. Не діє на себе: те саме юрособа/ФОП, той самий телефон, той самий email-домен закладу, та сама адреса — не рахується.

## 2. Дані (HUB, без обходу закладів)
- `venue:<id>.refCode` — короткий код (6 символів a–z0–9 без схожих o/0/l/1), унікальний, створюється при першому запиті або при створенні закладу.
- `lead:<id>.ref` — код з `?ref=` (зберегти у `leadAdd`, ≤ 20 символів, лише `[a-z0-9]`).
- `venue:<id>.refBy` — код того, хто привів (ставиться при створенні закладу з ліду/самореєстрації; **незмінний** після першої оплати).
- `venue:<id>.refPaid` — час, коли подарунок за цього закладу вже нараховано (захист від подвійного нарахування).
- `ref:<code>` → `{ venue, n: нараховано місяців, list: [{v, ts}], blocked }` — реєстр рефері (ліміт і журнал).
- Міграція — **нова** у `migrate.js`; стара поведінка (без полів) має працювати. Нічого не обходити по всіх закладах на запит: лічильники лежать у `ref:<code>`.

## 3. Нарахування (серверна логіка)
Точка: `billPaid()` у `worker/src/billing.js` — після того як оплату підтверджено (не `test`).
1. Якщо `v.refBy` є і `!v.refPaid` і це **перша реальна оплата** закладу (`pays` порожній до цієї) →
2. Знайти `ref:<refBy>`; якщо `blocked` або `n >= LIMIT` → нічого рахунку рефері, але **приведеному місяць дати** (він ні в чому не винен).
3. Інакше: рефері `paidTill += 30 дн` (через `venueBill`), `n++`, запис у `list`; приведеному `paidTill += 30 дн`.
4. Усе під одним замком, `refPaid = now` ставити в тій самій операції (ідемпотентність: повторний вебхук LiqPay не нарахує вдруге — вже є `payOnce`, використати).
5. Лог у журнал платформи + повідомлення власнику в кабінеті: «🎁 Ваш друг заплатив — +1 місяць» (без назви закладу, якщо він не дозволив).

## 4. Захист від зловживань
| Ризик | Захист |
|---|---|
| Самореферал (свої ж заклади) | `refBy` ≠ власний код і ≠ код закладів того самого акаунта (`acct.venues`); той самий email/телефон → не рахувати |
| Фейкові заклади заради місяців | Нараховувати лише після **реальної оплати ≥ 500 ₴** (не `test`, не 0), не за реєстрацію |
| Оплатив і одразу скасував/повернув | Подарунок «заморожений» 14 днів: `refHold = now+14d`; якщо `refund` у цей час — зняти |
| Багато місяців з одного коду | Ліміт [N]=12, `blocked` вручну власником у кабінеті «🚀 Продажі» |
| Розкрутка по колу (A→B→A) | Заборонити, якщо `refBy` закладу = заклад, що сам прийшов від нього (перевірка 1 рівня) |
| Підбір чужого коду | Код не секрет, але шкоди не дає; ліміт заявок з IP (3/год) уже є в `leadAdd` |
| Спам-посилання | Лише власник закладу бачить код; масові розсилки кодів у правилах заборонені (текст правил) |

## 5. Інтерфейс
- **Кабінет власника:** картка «🎁 Запросити друга»: посилання з кнопкою «Копіювати», тексти для месенджера (з marketing-sales), лічильник «Привели: X · Заплатили: Y · Подаровано місяців: Z із 12».
- **Лендинг:** рядок у футері «Приведіть заклад — місяць у подарунок обом» + сторінка `/ref` з правилами (5 рядків з §1).
- **CRM «🚀 Продажі»:** колонка «Джерело» = `ref`-код або назва закладу-рефері; фільтр; кнопка «заблокувати код».
- **Ручний режим (на старт, якщо автоматика не готова):** кнопка в картці закладу «🎁 +1 місяць» (запис у журнал, причина обов'язкова) — вже покриває бізнес без коду нарахування.

## 6. Події аналітики
`ref_click` (відкрито лендинг з `?ref`), `ref_lead` (заявка з ref), `ref_paid` (перша оплата), `ref_gift` (нараховано). Для воронки у CRM.

## 7. Тести (для `tools/selftest.mjs`)
1) Перша оплата приведеного → +30 дн обом, `refPaid` встановлено. 2) Повторна оплата/повторний вебхук → без нового нарахування. 3) Пробна/test-оплата → без нарахування. 4) Самореферал → без нарахування рефері. 5) Ліміт 12 → рефері без додаткового місяця, приведений отримує. 6) `blocked` код → те саме. 7) Закладу без `refBy` — поведінка як раніше.

## 8. Етапи
1. (мінімум, без коду нарахування) `?ref=` у заявку + колонка «Джерело» + ручна кнопка «🎁 +1 місяць» + посилання у кабінеті.
2. Автонарахування в `billPaid()` + ліміти + блокування.
3. Сторінка правил, події аналітики, повідомлення власнику.

## 9. Питання власнику (🔎)
- Ліміт подарункових місяців на рефері: 12? інше?
- Чи складається подарунок із безкоштовним першим місяцем (приведений: 2 місяці безкоштовно) — рекомендація: **так, але лише після першої оплати**, тобто місяць дається додатково до 1-ї оплати.
- Не-клієнти: % з першої оплати чи знижка? (рекомендація: разова знижка 250 ₴ на їхній заклад або подарунок — без грошових виплат, щоб не було податкових питань).
- Хто бачить, що друг привів: показувати назву чи лише «друг заплатив»?
